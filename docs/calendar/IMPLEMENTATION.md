# Реализация календаря

## Архитектура

Использованы существующие `User`, `Company`, `Interview` и права HR/администратора.
`Interview` остаётся общей моделью рабочих встреч и собеседований, поэтому подбор
и рабочий стол продолжают читать те же данные. Календарь не создаёт сотрудников
и не дублирует их учётные записи.

`CalendarSettings` хранит IANA timezone владельца и перерыв между встречами.
`CalendarAvailabilityRule` хранит повторяющиеся недельные окна в минутах местного
времени владельца. `CalendarBlock` задаёт исключения в конкретных UTC-интервалах.
Встречи и блокировки сохраняют начало в timezone-aware PostgreSQL timestamp.

Расчёт в `app/services/calendar.py` переводит рабочие окна в UTC, учитывает
занятость организатора и участников, перерывы и исключения. Публичные интервалы
не могут быть в прошлом. Период расчёта ограничен 31 днём. Не существующие при
переходе DST часы пропускаются; повторяющиеся часы имеют разные UTC-моменты.
Браузер группирует результаты по своим локальным датам и отображает местное время.

Все операции, влияющие на доступность, сериализуются блокировками существующих
строк пользователей. Участники блокируются в порядке UUID. Публичная запись
после получения блокировки повторно проверяет ссылку, расписание и занятость
в той же транзакции. Создание и редактирование внутренних встреч используют
те же блокировки. При конфликте возвращается HTTP 409. Для кандидатов используется
дополнительная блокировка строки кандидата. PostgreSQL READ COMMITTED является
рабочей конфигурацией; SQLite используется только для быстрых тестов поведения.

Ссылки содержат случайный токен, относятся к одному существующему пользователю
компании и имеют состояния включена/отключена/отозвана. Отзыв необратим для старого
токена; повторное включение создаёт новый. Уникальный индекс ограничивает владельца
одной неотозванной ссылкой. Публичное API проверяет активность компании и владельца.
Публичный HTTP-клиент не отправляет JWT и заголовок режима поддержки из CRM.
nginx ограничивает запросы публичной записи, объём тела запроса и отключает кеш.

## Будущая синхронизация

`CalendarChange` — постоянный журнал событий `created`, `updated`, `cancelled`.
Событие и изменение встречи фиксируются одной транзакцией. Данные отмены остаются
после удаления встречи. `payload.version = 1`, `id` события служит ключом
идемпотентности будущего обработчика. Поле `processed_at` предназначено для
подтверждения обработки. Будущий адаптер должен хранить соответствие локальных
и внешних идентификаторов и обрабатывать события по порядку с повторами.
Сейчас нет сетевых адаптеров или фонового обработчика внешних календарей.

## Изменённые и добавленные файлы

Backend:

- `backend/app/api/v1/recruitment.py` — защищённые CRUD/API, блокировки,
  отключение/отзыв ссылки, публичное бронирование, журнал событий.
- `backend/app/services/calendar.py` — расчёт интервалов, UTC/IANA, DST,
  ограничения диапазона и общие транзакционные блокировки.
- `backend/app/models/calendar.py` — настройки и журнал изменений.
- `backend/app/models/__init__.py` — регистрация новых моделей.
- `backend/app/schemas/recruitment.py` — валидация расписания, timezone, перерывов,
  исключений, публичной записи и обязательных полей редактируемой встречи.
- `backend/alembic/versions/019_calendar_settings_changes.py` — новые таблицы,
  индексы и ограничение активных ссылок; совместимость с миграцией 018.
- `backend/requirements.txt` — база IANA timezone для Windows и окружений без tzdata.

Frontend:

- `frontend/src/pages/CalendarPage.tsx` — утверждённый командный центр на данных API.
- `frontend/src/pages/PublicBookingPage.tsx` — утверждённая последовательная запись.
- `frontend/src/components/calendar/CalendarUI.tsx` — иконки, бренд и аватары макета.
- `frontend/src/components/calendar/CalendarDesign.css` — стили Figma с локальной областью.
- `frontend/src/components/calendar/CalendarControls.css` — поля, состояния и адаптация форм.
- `frontend/src/components/calendar/CalendarModal.tsx` — модальное окно с управлением фокусом.
- `frontend/src/components/calendar/MeetingDialogs.tsx` — встречи и исключения.
- `frontend/src/components/calendar/AvailabilityDialog.tsx` — три раздела настроек.
- `frontend/src/api/workspace.ts` — API календаря и отдельный публичный HTTP-клиент.
- `frontend/src/api/client.ts` — истёкший вход в CRM не прерывает публичную запись.
- `frontend/nginx.conf` — защита публичного API на уровне reverse proxy.

Проверки и документация:

- `backend/tests/test_calendar_booking.py` — поведение, права, приватность,
  часовые пояса/DST, исключения, журнал и валидация.

## Проверки

Проверено локально 6 октября 2026 года:

- Все 75 backend-тестов прошли, включая 3 теста настоящих конкурентных
  транзакций PostgreSQL. В 12 одновременных запросах на один слот успешен один.
- Полный браузерный набор: 52 теста прошли на desktop/mobile; 8 интеграционных
  сценариев без отдельного тестового аккаунта пропущены.
- Живой сценарий календаря дополнительно запущен отдельно: 1 тест прошёл
  с FastAPI и PostgreSQL, включая перезагрузку, гостя в America/New_York,
  редактирование и отмену.
- TypeScript и production-сборка Vite прошли. Есть предупреждение о размере
  общего JS bundle (534 kB) и существующее предупреждение `utcnow()` в HH API.
- Миграции 000–019 применены к новой изолированной PostgreSQL БД.
  Производственная БД не изменялась. Конфигурация nginx проверена по коду;
  её запуск следует проверить при развёртывании.

Переходы DST проверены для весенних отсутствующих часов, повторяющихся осенних
часов и отдельных окон в повторяющемся часе. Редактирование названия сохраняет
исходный UTC-момент и длительность встречи; для неоднозначного местного времени
редактор показывает выбор смещения.

```powershell
# Быстрые проверки backend
cd backend
python -m pytest -q

# Настоящие транзакции: только отдельная мигрированная тестовая БД!
$env:CALENDAR_TEST_DATABASE_URL='postgresql+asyncpg://user:password@localhost:5432/calendar_test'
python -m pytest tests/test_calendar_postgres.py -q

cd ../frontend
npm run build
npm run test:e2e
```

Живой браузерный тест запускается отдельно при наличии активированного HR аккаунта
`calendar-e2e@example.org` в изолированной БД и запущенного backend на localhost:8000.
Тест меняет его расписание и ссылки; не запускать с производственной БД.

```powershell
$env:CALENDAR_E2E_PASSWORD='<password of isolated test account>'
npm run test:e2e -- e2e/calendar-live.spec.ts --project=desktop --workers=1
```

## Ручная приёмка

1. Применить миграцию 019, войти HR и открыть календарь.
2. Задать часы, timezone, длительность и перерывы. Перезагрузить страницу;
   настройки должны сохраниться.
3. Создать встречу с существующим сотрудником, перезагрузить, изменить и отменить.
4. Добавить частичную блокировку и выходной на целый день. Эти интервалы должны
   исчезнуть из свободных слотов; после удаления исключения снова появиться.
5. Включить ссылку и открыть её в инкогнито. Проверить запись без входа и появление
   встречи в CRM; внутренние данные в ответах публичного API отсутствуют.
6. Одновременно отправить запись на один слот из двух окон: успешна одна запись,
   второе окно получает конфликт и обновлённые слоты.
7. Проверить два браузера с разными IANA timezone, особенно дату рядом с полуночью
   и переходом DST. UTC-момент одной встречи должен совпадать.
8. Отключить/включить ссылку и отозвать её. После отзыва старый токен недействителен.
9. Проверить подбор, сотрудников, учебные материалы и обычный вход в CRM.

Старые правила 018 не содержали timezone. Перед использованием их нужно один раз
сохранить с правильным часовым поясом; до этого применяется UTC.
